# エラー・注記の診断

エクスポートが失敗したときは、管理一覧で該当する版の **「エラー・注記の診断」** を開く。管理者向けの失敗通知にも該当画面へのリンクがある。`local/tomb:manage` が必要で、学生・教師は自分の版でもこの画面・JSONを取得できない。

## 確認する順序

1. 収集状態とZIP状態を確認する。収集済みでもZIP組立で失敗する場合がある。
2. 失敗時刻、処理段階、コースID・活動ID、例外文を確認する。活動IDはMoodleのコースモジュールID。
3. 経過時間、PHPメモリ上限、使用量・プロセスピーク、PHP実行時間上限を確認する。上限の値だけでタイムアウトやメモリ不足と断定しない。
4. 「例外・呼出し経路・処理件数の詳細」でエラー型・コード、コード内の場所、引数を除いた呼出し経路、保存済みエントリ数、注記内訳、Moodle・PHP・Tombの版を確認する。
5. 必要に応じて「診断情報をJSONで取得」で調査資料を保存する。

**「保存内容に380件の注記があります」の380件は、コンテンツ数や上限ではない。** 未対応形式、レビュー制限、権限による除外、描画失敗などの理由別件数を確認する。通常の仕様による注記だけで要求全体が失敗するわけではない。診断画面は失敗してZIPができていない版でも注記の内訳を表示する。活動別は最初の100組、理由別合計は全件を対象とする。

処理段階の主な値は `inventory`（見積もり）、`collecting`（対象の収集）、`activity`（教材・活動）、`grades`（成績）、`finalising`（HTML固定）、`link_validation`（内部参照検証）、`planning`（ZIP配置計算）、`preparation`（ZIP受付・通知）、`assembly`（ZIP組立）。活動内のファイル・設問の失敗は `file` / `question` としても記録する。

## 記録する範囲と限界

通常の例外に加え、PHPの終了処理が実行される致命的エラーを可能な範囲で記録する。処理の実行時間・メモリ制限は変更しない。致命的エラー後の状態修復・通知は既存の清掃タスクが担当する。

OSによる強制終了、接続断、DB障害などでは詳細を保存できない場合がある。終了処理が走らなかったワーカーは、ロックが解放され、最終ハートビートから10分以上経過したことを清掃タスクが確認した時点で「中断」を記録する。この場合、原因や停止時のメモリ使用量は不明として扱い、PHP・cron・サーバのログと時刻・版IDを照合する。ログ保存自体に失敗した場合はPHPログに版ID付きの短い案内を出す。

ピークメモリはPHPプロセス全体の値で、同じプロセスで先に実行した仕事を含むことがある。0秒のPHP実行時間上限は無制限を表すが、OSやcronの外部制限は別途存在し得る。

## 保存期間と情報の扱い

各版で、部分保存に失敗した警告は最初の25件、処理の失敗・中断は直近25件を保持する。多数の同種エラーでは警告の詳細を打ち切るが、注記の理由別合計は全件を確認できる。通常cronで30日を過ぎた診断ログを削除する。材料の明示削除と承認済みPrivacy削除でも対象ログを削除する。診断の保存期間は既存の要求・監査・注記の保存期間を変更しない。

リトライで最終エラー表示が消えても、保存期間内の診断履歴は残る。機能導入前の失敗について、呼出し経路・メモリなどを後から復元することはできない。既存の最終エラーと注記の内訳は確認できる。

ログには提出物・解答本文、例外の引数・オブジェクト、MoodleのSQLデバッグ情報、HTTP要求やセッション全体を取り込まない。例外文のメール、URL、絶対パス、一般的な認証キーの値をマスクする。例外文に含まれる全ての個人情報・秘密情報の検出を保証するものではないため、第三者へJSONを渡す前に管理者が内容を確認する。通常の学習ZIPには診断ログを含めない。

## 動作確認

`php local/tomb/tests/diagnostics.php --run` は専用のTomb検証データと検証モードを必須とする。合成要求で収集・ZIP組立の失敗、メッセージのマスク、引数の除外、件数制限、管理権限、保持期間、材料削除とPrivacy削除を検証し、DB変更をロールバックする。実際の教材や100人分の出力を失敗させる試験ではない。
