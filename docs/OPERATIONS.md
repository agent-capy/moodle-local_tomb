# 運用・開発手順

## 共有環境での導入

設置先は Moodle の `local/tomb`。独立した Git リポジトリは `moodle-local_tomb` とする。Moodle 本体・他プラグイン・OS・サービス設定は変更しない。

導入前に他プラグインのソースと DB 版を確認する。専用 `cli/install.php` は全プラグインの一致を確認し、`local` 型の更新処理でも Tomb 以外への更新コールバックを拒否する。CLI プロセス内でクラス・言語キャッシュを更新し、導入完了のバージョン情報を記録する。サイト全体のアップグレード CLI は実行しない。

新規配置は、完全なディレクトリを用意してから行い、導入完了まで連続して実施する。Moodle が新プラグインを検出してから導入が完了するまでは、通常 cron が保留される場合がある。完了後は `moodle_needs_upgrading()` が false であること、通常ログイン・コース表示・通常 cron の完了を確認する。

既存 Tomb の更新前には、そのディレクトリと Tomb の設定・テーブルを必要に応じて保全する。復旧時にサイト全体の DB リストアや初期化を行わない。アルファ版開発時に発見した導入不備（予約語の列名と Moodle 5.0 の通知定数）は修正済み。現行の列名は `zipoffset`。

## 設定

| 項目 | 既定・扱い |
|---|---|
| 運用モード | `disabled`。管理画面で変更・監査 |
| 検証 | `rehearsal`。指定コーホートに限定、架空の配送期限は設定しない |
| 本番 | `active`。配送期限と環境確認が必要 |
| 配信のみ | `delivery_only`。新しい収集要求を受け付けない |
| 配送期限 | Unix timestamp。期限後は取得停止し、材料は削除操作まで保持 |
| ZIP キャッシュ | 合計2 GiB、TTL最長21600秒。使用中のキャッシュは削除しない |
| 空き容量 | 5 GiBとボリュームの10%の大きい方。生成時はデータ・一時領域も確認 |
| ZIP置場 | 既定 `moodledata/local_tomb_cache`。Webルート外を必須とする |
| 生成・組立 | 全体で1件のワーカーロック |
| 配信数 | 既定1、設定は1〜8に制限 |
| 新版の間隔 | 既定300秒。同じ版のキャッシュ再構成は別扱い |

期限は配送用 ZIP キャッシュの期限とは別である。キャッシュが消えても、材料が残り利用資格があれば同じ版を再準備できる。期限後の材料削除は管理画面で版を選び、再取得不能になることを確認して実施する。元の Moodle 資料・他プラグインのファイルは削除しない。組立計画・注記・監査は残す。

本番への切り替え前に、検証版の材料を管理画面で明示的に削除し、監査記録を保持する。モードを変えるだけで検証版を本番として配信することはできない。アルファ版は移行時の検証材料の自動一括削除を行わない。

## 通知・取得・監査

通常の Moodle cron を使う。Tomb 専用の常駐サービスは不要。画面に cron 停滞を表示する。共有サイトで試験のために全 cron を手動で一斉実行しない。

通知は Moodle の通知機構を利用し、既定ではサイト内通知を有効にする。メールは許可のみで、既定有効にはしない。教師代行では、収集完了を本人へ通知し、本人が ZIP 準備を依頼する。教師の進捗画面には学生版の取得リンクを置かない。管理者の取得は実行者 ID と対象版を監査する。

通知済み・ダウンロード開始・本人による「展開して記録を確認しました」は別の記録である。受領 CSV は版単位。本番と検証を混ぜずに絞り込み、未受領の版へ手動リマインドできる。

監査は SHA-256 による連鎖を検証できる。DB 全体を書き換えられる者への改ざん防止装置ではない。独立した照合を必要とする場合は、権限付き JSONL 出力を別の保管先に保持する。

## 障害時

| 表示・原因 | 対応 |
|---|---|
| 受付のまま | `cli/status.php` と通常 cron を確認。モード・コーホート・期限も確認 |
| 容量待機 | 容量制限と空きを確認。清掃タスクが待機要求を再受付する |
| 単一ZIPが上限超過 | 設定確認を明示する。無期限に待機しない |
| キャッシュ破損 | 検出したキャッシュを破棄し、本人が同じ版の再準備を要求 |
| 保存材料の欠損 | 該当版を配信停止。本人と管理者へ通知し、別の版として再生成 |
| ワーカー中断 | ロックの非保持と10分以上の古いハートビートを確認して整理。収集は失敗表示、組立は固定材料から再受付 |
| 取得期限切れ | 取得を停止。材料削除は別の明示操作 |

空き容量ガードが収集中に作動した場合、アルファ版はその要求を失敗として知らせる。空きを確保して新しい版を依頼する。部分生成を正常な完成品として渡さない。

## 検証用データ

`cli/fixture.php --create --secrets=/private/tomb-fixture.json` で専用コース、コーホート、学生2名・教師1名を作成できる。JSON は `password` に16文字以上のランダムなパスワードを指定し、CLI 実行者だけが読み書きできる0600のファイルとして事前に用意する。コース・アカウントの識別子は `tomb-alpha-fixture` / `tomb.alpha.*`。同名で識別子の違う利用者は再利用しない。

小テストの検証では、サイトに存在する5形式のテスト問題への参照を専用小テストへ追加し、専用学生の受験を新規作成する。元の問題や既存受験を変更しない。自動生成するアカウントのメールは `example.invalid` で外部交付に使わない。

`tests/integration.php --run` はこの専用コースと検証モードを必須とする。新しい試験版を作り、その版の材料欠損・削除を再現する。小テストのレビュー設定は `finally` で復元する。`tests/named_export.php --run` は専用コース内だけで実名権限を一時付与し、理由と監査を確認後に復元する。`tests/cache_lifecycle.php` は破損させてよい専用学生版のキャッシュだけを指定して実行し、別PHPプロセスのロックで配信中を再現する。サイト全体のテスト DB 初期化は行わない。

本番データを含む生成 ZIP、認証状態、アカウントのパスワードファイルを Git に入れない。配布物作成先 `build/`、検証出力 `test-output/` は Git の対象外。
